# E21c: the name of a FARP, and names that differ by case

Question: when a script spawns a FARP static with a chosen `name`, does DCS use that name
as the airbase's name, and what else shows up as its name? Follow-up questions from the
owner: do the platform's candidate names survive, do names that differ only in case stay
apart, and what does the map show.

## Setup

- Script: `lua/experiments/e21c-farp-name.lua`, run with `cargo xtask eval <client> server`.
  It ran in three passes in one mission: spawns 1 to 3, then the naming-scheme spawns
  (part 4 and 5), then the case pairs (part 6). The file skips a part whose names exist.
- DCS build: 2.9.31.29434 (LIVE, `cargo xtask target check`).
- Platform: Windows client (Windows NT 10.0.26200.0), DCS started through its scheduled
  task in the logged-in desktop session. Nothing connected to a server.
- The mission was a private hosted session with the shell mission from `cargo xtask miz`,
  not a single-player mission. It listened on a non-default port, was not public, and
  nobody joined. The tooling has no other way to give the client a mission scripting state.
- Date: 2026-11-15. The mission was paused at model time 0 throughout.
- Screenshots were taken with `DCS.makeScreenShot()` from the hook state after
  `DCS.setScreenShotExt('.png')`. The signatures are inferred from a call that returned
  without error and wrote a file (LIVE). The extension argument was given with its dot and
  the file name came out with a double dot (LIVE).

Every FARP was spawned with `coalition.addStaticObject` as `type = 'FARP'`,
`category = 'Heliports'`, `shape_name = 'FARPS'`, with a callsign id and a frequency.

## Results of the probe

LIVE unless tagged otherwise.

| Read | `Bravo Test` (first) | `np!k3F2A` |
|---|---|---|
| `Airbase.getByName(name)` | found | found |
| `getName()` | `Bravo Test` | `np!k3F2A` |
| `getCallsign()` | `London` | `Dallas` |
| `getID()` | 1000000 | 1000002 |
| `getCategory()` | 4 | 4 |
| `StaticObject.getByName(name)` | found, same ID | found, same ID |
| entry in `world.getAirbases()` | `Bravo Test`, `London`, 1000000 | `np!k3F2A`, `Dallas`, 1000002 |

- DCS uses the chosen `name` as the airbase name. The callsign is a separate value that
  DCS picks from the callsign id (ids 1, 2 and 3 read `London`, `Dallas` and `Paris`; id 6 read
  `Rome` on the map). `getDesc()` has `displayName = FARP` and `typeName = FARP`.
- The platform-style name `np!k3F2A` works as a name for both the static and the airbase.
- `world.getAirbases()` held 21 airbases before the spawns and 23 after the first two.

### A second FARP with the same name

- Spawning a second FARP named `Bravo Test` made the first one's static and airbase object
  report `isExist() == false`. Both old objects still answer `getName()` with
  `Bravo Test`.
- `Airbase.getByName('Bravo Test')` and `StaticObject.getByName('Bravo Test')` return the
  new FARP, 600 m east of the first. The old object is not the same object.
- `world.getAirbases()` still lists the removed FARP: the count went from 23 to 24, and the
  list holds two entries named `Bravo Test`, both with ID 1000000 (the new one reports
  callsign `Paris`). I did not read `isExist` on the stale list entry.
- `np!k3F2A` is unaffected.

### The naming scheme (base 62, campaign tag `k3F`) and the current spec form

All six names were found by `getByName` of their kind, and `getName()` returned each
byte for byte, with `isExist() == true`:

- group `np#k3F7`; units `np.k3F19` and `np.k3F1A`
- static (FARP) `np!k3F2B`, also found by `Airbase.getByName`
- group `np.g.m3k9x2a1.7`; unit `np.u.m3k9x2a1.1z`

Units, a static and a group with these names coexist: `np.k3F19`, `np.k3F1A`, `np!k3F2B`,
`np!k3F2A` and group `np#k3F7` all existed after the spawns. This does not test a unit
and a static with the same name.

### Case

Each pair kept both objects (`isExist() == true`), with distinct IDs and distinct objects,
and `getName()` returned the exact case:

| Pair | IDs |
|---|---|
| units `np.k3F19`, `np.k3f19` | 1000007, 1000016 |
| statics `np!k3F2B`, `np!K3F2B` (FARPs; also two airbases) | 1000009, 1000017 |
| groups `np#k3F7` (2 units), `np#K3F7` (1 unit) | 1000006, 1000013 |
| unit `np.x9Z1`, static `np!X9z1` (a FARP) | 1000020, 1000021 |

Names are case sensitive for units, statics, groups and airbases, so base-62 names that
differ only in case do not collide (LIVE, one pair of each kind). The two spawns of the
unit-vs-static pair used different name prefixes, so this shows case, not a shared
namespace.

## What the F10 map shows

Observed by the owner on the client's F10 map in the same mission (screens kept outside
the repository). LIVE.

- The label drawn for a FARP is its type, `FARP`, not its name. Ground units are labeled
  with their type, `M113`.
- Selecting a FARP opens an info box with GROUP = the static's name (`np!X9z1`), TYPE =
  `FARP`, COUNTRY, and CALLSIGN = the callsign and frequency (`Rome,127.500 MHz`).
- Selecting a ground unit opens an info box with GROUP = the group's name (`np#x9`),
  TYPE = the unit's type (`APC M113`), and CALLSIGN = the unit's name (`np.x9Z1`).
- The FARP named `Bravo Test` that the second spawn removed is still drawn on the map:
  seven FARPs showed, six live and the removed one.
- The radio menu was not checked. The owner believes it does not show the FARP name
  (UNVERIFIED).

## Reading

- A script's chosen name is the name every script read returns for a FARP, so a platform
  that names its FARPs reads them back by that name (LIVE).
- A FARP's callsign is not the chosen name and cannot be set by it. The name is not shown
  on the F10 map's label; the info box shows it as GROUP (LIVE).
- A second spawn with a taken name replaces the first for script reads but the first
  stays drawn and listed in `world.getAirbases()`. A platform should not reuse a FARP name
  (LIVE for this build).
- No claim here comes from Eagle Dynamics' files (no ED-CODE).
