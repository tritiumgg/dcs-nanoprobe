## The live check

The scenario creates a campaign and two statics of type `FARP Fuel Depot` 1,500 m
apart on land: one alive (`killed`), one with `StaticSpec.dead` (`born`). At each phase
it reads the World service and, in DCS's server state, `StaticObject.getByName`,
`getLife` and `isExist` for both names. A phase passes when the static is listed in
state `dead` with `alive` false and DCS finds it with life 0 or less. Run 2 also
requires an empty `last_error`, which shows that no ruin's spawn was refused, and has
the phase `cleared`.

| Phase | What happened | `killed` in DCS | `born` in DCS | World service, both |
|---|---|---|---|---|
| `spawned` | Both put; simulation running | found, life 10, exists | found, life 0, not existing | `killed` live and alive; `born` dead, not alive |
| `killed` | `trigger.action.explosion` of power 1,000 at `killed`'s point | found, life 0, not existing | unchanged | dead, not alive |
| `reload` | The campaign's mission loaded again; it starts paused | found, life 0, not existing | found, life 0, not existing | dead, not alive |
| `dcs_restart` | DCS and the sidecar stopped; DCS restarted, the campaign's mission loaded, the sidecar started from its store; paused | found, life 0, not existing | found, life 0, not existing | dead, not alive |
| `running` | The simulation ran for 10 s | found, life 0, not existing | found, life 0, not existing | dead, not alive |
| `cleared` (run 2) | `ClearDebris` of a box around each static, 400 m square, from 500 m below sea level to 5,000 m above; then 5 s of simulation | found, life 0, not existing | found, life 0, not existing | dead, not alive |
| `removed` | `RemoveEntity` of both, simulation running | not found | not found | not listed |

The reads were the same in both runs.

What the runs show:

- **A static added dead while paused.** After the reload and after the restart the
  mission was paused, and the sidecar's `STATIC_SPAWN` with `dead = true` produced a
  static that reads life 0 and `isExist` false at once. `StaticObject.getByName` finds
  it. In run 2 the store held no error for either spawn, so neither was refused. The
  runs recorded no result code: that the handler answered `APPLIED` with the static's
  ID is inferred from the shim, which answers `DCS_REFUSED` when
  `coalition.addStaticObject` returns nothing or an object with no ID. A live
  `FARP Fuel Depot` reads life 10.
- **The explosion kills the static in place.** After the kill the same name still
  resolves, with life 0 and `isExist` false, and the store held a death fact for it
  within the scenario's 180 s wait.
- **`world.removeJunk` leaves a static added dead.** After the restart both statics
  were ones the sidecar had added dead. Each `ClearDebris` was `APPLIED` with a count of
  0, and both statics kept their reads. That each box held its static follows from the
  box's size and place, not from a count: the handler skips a managed static without
  counting it. docs/results/2026-11-17-person-fixes.md saw a 250 km box clear remove
  statics added dead that nobody managed; there the handler's own destroy applies to
  them.
- **`STATIC_DESTROY` removes a static added dead, found by its name.** After
  `RemoveEntity`, `StaticObject.getByName` found neither name. Both statics were ones
  added with `dead = true` by then. The read was a later eval call than the destroy,
  with the simulation running. Earlier results differ for a static an explosion killed:
  docs/results/2026-11-16-person-tests-2.md still found one by name after
  `Object.destroy`, docs/results/2026-11-16-clear-debris.md did not, and
  docs/results/2026-11-17-person-fixes.md found one in the same call as its `destroy`.
  Whether `getByName` finds a destroyed static that an explosion killed is not settled.
- **The ruin survives the simulation running.** Ten seconds of model time changed no
  read.

The scenario polls every 5 s. It does not show that the killed static was never alive
between two polls after a restore; the fake sim's checks cover that (below).

Not re-checked here: what a client sees. No client took part. That a `FARP Fuel Depot`
added dead shows destroyed on a client, and that `Object.destroy` removes a ruin from a
client, are LIVE in docs/results/2026-11-17-person-fixes.md, on the same DCS build.

## Limits

- What a ruin looks like after a restore is DCS's model for a dead static of the type.
  A `Windsock` added dead shows intact, a `BRDM-2` shows alive and then not at all, and
  a `speedboat` is refused (LIVE, docs/results/2026-11-17-person-fixes.md). The
  platform adds no workaround. Which other types behave so is UNVERIFIED.
- A static that left DCS with no death and is then called dead, by the lost policy or
  by `ResolveMember`, gets its ruin in the next mission generation: in its own, the
  agent still holds its spec revision and answers the ruin's spawn `AT_REVISION`.
- The sidecar does not observe a ruin. One that another script removes is spawned
  again in the next generation.
- A static whose death event the mission's end cut off has no death fact and is no
  ruin.
- A refused ruin's spawn is not sent again in its generation by the same sidecar
  process; a restarted sidecar tries once more.
